# 프로젝트 헌장 — 산스 인생책 로마쇠망사 자료실

이 문서는 이 프로젝트의 **바꾸기 어려운 결정**을 담는다. 코드 리뷰와 스펙 검토가 이 문서를 기준으로 판정한다. 여기 어긋나는 코드는 리뷰에서 되돌린다.

> **이 파일은 미러다.** 정본은 볼트 `Works/로마쇠망사_자료실/CONSTITUTION.md`이고 여기는 실행·코드리뷰용 사본이다. 원칙이 바뀌면 **볼트를 먼저 고치고** 이 파일을 맞춘다. 두 벌을 따로 쓰지 않는다.

## 0. 이 도구의 크기 — 다른 모든 조항보다 위에 있다

2026-08-13 모더레이터와의 1:1에서 나온 것이다. 아래 넷이 어긋나면 코드가 아무리 깨끗해도 실패한 것이다. **1~10절이 "어떻게 잘 만드나"라면 0절은 "무엇을 만들지 말아야 하나"다.**

**0-1. 이 도구는 헷갈림을 덜어주는 만큼만 존재한다.** 자랑하려고 만드는 물건이 아니다. 사람들이 실제로 헷갈려 하는 지점 — 누가 누구와 적이고 누가 편인지, 그게 시간이 지나며 어떻게 뒤집히는지 — 딱 거기까지다. 특히 가계도다.

**0-2. 완성이 목표가 아니다. 진짜 쓰임 하나가 목표다.** 이 물건의 진짜 문제는 양이 아니라 "이걸 왜, 어떻게 쓰지?"에 답이 없다는 것이다. 그 하나는 볼트 `USECASE.md`에 적혀 있다 — **발표 담당자가 인물 파트를 준비한다.** 기능 목록이 아니라 이 시나리오가 판정 기준이다.

**0-3. 뒷단과 앞단을 가른다.** 데이터 정비는 계속 굴리되 **사람 앞에 내놓는 자리는 최대한 심플하게** 간다. 뒷단이 방대하다는 것이 앞단이 복잡해도 된다는 뜻이 아니다. 반대다 — 뒷단이 방대하니까 앞단이 골라줘야 한다.

**0-4. 급하게 가지 않는다.** 책을 다 읽고 나서도 계속 쓸 물건이다. **기한에 쫓겨 범위를 늘리지 않는다.**

> **판정 질문** — 기능을 넣을지 말지 막힐 때 이것을 묻는다.
> *"이게 사람들이 헷갈려 하는 지점을 덜어주나, 아니면 우리가 만든 걸 보여주나?"*
> 뒤쪽이면 넣지 않는다. 코드 리뷰(7절)에서도 이 질문을 한 번 던진다.

## 1. 이 프로젝트가 무엇인가

에드워드 기번 『로마제국쇠망사』의 한국어 편역본(30포인트)과 기번 영문 원전, 그리고 거기서 뽑은 **인물·장소·사건 644개 + 관계 667개짜리 지식그래프**를 편데 운영팀이 쓸 수 있게 만드는 정적 웹사이트다.

팀은 자료를 이미 갖고 있다. 문제는 **못 쓴다는 것**이다. 깃을 아는 사람이 하나뿐이고, 갱신이 오면 각자 다시 받아야 하고, AI에게 무엇을 줘야 할지 모른다. 이 사이트가 그 사이를 메운다.

- 독자: 편데 운영팀. AI 초보는 아니지만 스펙트럼이 넓다
- 규모: 1인 개발 + AI 에이전트 병렬
- 공개: 누구나 볼 수 있는 URL이지만 `noindex`. 링크는 팀 내부로만 돈다

### 성공 기준

1. 깃을 못 쓰는 팀원이 **설치 없이** 브라우저에서 본문과 객체 관계를 본다
2. 갱신이 오면 **다시 받지 않아도** 사이트가 이미 바뀌어 있다
3. 원하는 포인트의 객체 데이터를 **시트로 내려받거나 복사**한다
4. 틀린 데이터가 팀에게 **도달하지 않는다** — 빌드가 막는다

## 2. 백엔드는 없다

**서버도 API도 데이터베이스도 없다.** `output: 'export'`로 정적 HTML을 뽑아 Vercel에 얹는다. 런타임에 도는 서버 코드는 0줄이다.

"백엔드"에 해당하는 것은 **빌드 시점 데이터 파이프라인**이다.

```
ontology/*.jsonl · entities/**.md · points/*.md   (레포 루트, 정본)
        │
        ├── lib/ontology.ts        Zod 검증 + 불변식 검사   ← 게이트
        ├── lib/<도메인>/           로딩·변환·조회
        │
        └── app/**                 조립만. 로직 없음
                │
                └── out/           정적 HTML → Vercel
```

이 결정이 헌장에 있는 이유: **누군가 "API 하나만 만들면 편한데"라고 말하는 순간 위 성공 기준 2번이 깨진다.** 서버가 생기면 배포가 복잡해지고, 데이터가 런타임에 바뀔 수 있게 되며, 빌드 게이트가 무력해진다. API가 정말 필요하면 그건 헌장을 고칠 사안이다.

**마크다운 렌더러를 안 넣는다 (2026-08-14, 실측 근거).** `next-mdx-remote`(MPL-2.0)와 `remark-wiki-link`를 넣기로 했다가 뺐다 — **astryx가 `Markdown`을 이미 준다.** 필수 prop은 `children: string` 하나고, GFM 표·코드블록·이미지·체크리스트를 지원하며, 자체 파서라 외부 의존성이 0이다(`package.json` dependencies는 `intl-messageformat` 하나뿐). 위키링크 `[[X]]`만 마크다운이 아니라서 `lib/doc.ts`의 정규식 한 줄이 평문으로 편다.

단 **`parseOutlineFromMarkdown`은 안 쓴다.** 슬러그를 `[^a-z0-9]+`로 만들어서 한글 제목이 전부 빈 문자열이 되고 id가 통째로 겹친다. 목차는 `lib/doc.ts`의 `docSections()`가 H2로 잘라 만든다.

### astryx에 있는 것을 손으로 다시 만들지 않는다

**쓰기 전에 `node_modules/@astryxdesign/core/dist/`에 그 컴포넌트가 있는지 본다.** 97개가 들어 있고, 문서 사이트 골격(`AppShell`·`TopNav`·`SideNav`·`Breadcrumbs`·`Section`·`Outline`·`Markdown`·`CodeBlock`·`Banner`·`Badge`·`Collapsible`·`MetadataList`·`Grid`·`List`)은 **필수 함수 prop이 없어 서버 컴포넌트에서 그대로 돈다.**

이 조항이 생긴 이유: 2026-08-14에 셸을 통째로 다시 만들었다. `DESIGN.md`가 「3단(좌 사이드바 + 중앙 본문 + 우 목차)」을 이미 적어뒀는데도 구현이 `Stack`과 텍스트 링크로 직접 조립해 8개 컴포넌트만 쓰고 있었고, River가 화면을 보고 반려했다. **기획을 안 읽어서가 아니라 라이브러리를 안 읽어서 생긴 사고다.**

클라이언트 래퍼가 필요한 것은 넷뿐이다 — `CommandPalette`·`TabList`/`SegmentedControl`·`Pagination`·`Lightbox`. 전부 필수 prop에 `onChange` 계열 함수가 있다.

**`pagefind`는 뺐다 (2026-08-14, 실측 근거).** 한국어 스테머가 없어 중간 일치가 안 되고(`이사르`로 `카이사르`를 못 찾는다), 알파벳 버킷팅 탓에 한글 인덱스가 **441KB 단일 청크**로 통째로 내려온다(첫 검색 554KB). 객체 644개는 `es-hangul` 인메모리 필터가 더 낫고 **초성 검색이 덤으로 붙는다.** 되살릴 조건은 본문 200개 초과인데 30포인트가 전부라 그럴 일이 없다.

**그래프 라이브러리는 클라이언트에 안 싣는다 — 예외 하나가 조건부로 열려 있다 (2026-08-16 개정).** 원래 조항은 예외 없이 "싣지 않는다"였다. 빌드타임에 좌표를 계산하고 순수 SVG로 굽는다는 것이고, 지키려던 것은 둘이었다 — **인물 이름이 HTML 텍스트로 남아 Ctrl+F에 잡힐 것**, **외부 CSS가 없어 astryx와 부딪힐 면이 0일 것**.

**2026-08-16에 `d3-force@3.0.0`(ISC, min 8.3KB)을 ego 관계 그래프 한정으로 넣었다.** 뒤집은 게 아니라 지키려던 둘을 다른 방법으로 살리고 예외를 명문화한 것이다.

- *Ctrl+F* → **살렸다.** 관계 목록이 그림 옆에 **정적 HTML 텍스트로 따로** 있다(`components/EntityAside.tsx`). 그림은 보조 시각화지 유일한 표현이 아니다. **이게 예외의 조건이다** — 목록이 사라지면 예외도 같이 사라진다. 리뷰에서 이 조건을 본다
- *CSS 충돌* → 렌더는 우리 SVG다. `d3-force`는 힘 계산만 하고 DOM도 CSS도 만들지 않는다. 외부 CSS 0
- **가계도(`lib/family/`)는 그대로 빌드타임 SVG다.** 세대를 행으로 고정하는 문법이라 힘 시뮬레이션이 오히려 해롭다. 예외는 ego 관계 그래프 한 화면에만 적용된다

React Flow(MIT, 87KB)는 여전히 폴백이고 승격 조건은 노드 드래그·자유 pan/zoom이다.

**같은 뼈대가 세 번 반복되면 마크다운이 아니라 데이터다 (2026-08-16 신설).** 「언제·재료·프롬프트·나오는 것」처럼 **같은 라벨 묶음이 항목마다 되풀이되면 그건 산문이 아니라 표의 성질**이다. 마크다운으로 쓰면 `**언제** 발표 전에 …`처럼 라벨이 본문과 한 줄로 흘러 항목 경계가 사라진다. River가 활용하기를 두 번 반려한 원인이 매번 이것이었다("가독성이 너무 안 좋다, 사용자적 관점의 UXUI와 라이팅이 되어 있지 않다").

그런 화면은 `lib/<이름>.ts`에 필드로 두고 `components/<이름>Card.tsx`가 그린다. 라벨은 `MetadataList`의 왼쪽 칸으로 빼고, 사람이 붙여넣을 문구는 `CodeBlock hasCopyButton`으로 낸다. 지금 이 규칙을 따르는 것은 `recipes`·`skills`·`pitfalls`·`materials` 넷이다.

**딸린 마크다운을 남겨두지 않는다.** 프론트매터 한 줄(`summary`)을 읽으려고 원본 `.md`를 남기면 카드와 산문이 두 벌로 갈라져 반드시 어긋난다. `content/use/*.md` 361줄이 그렇게 떠 있다가 2026-08-16에 삭제됐다. 데이터로 옮겼으면 마크다운은 지우고, 요약 한 줄은 화면이 직접 갖는다.

**블록 주석에 `*/`를 넣지 않는다.** `.agent/skills/*/SKILL.md` 같은 글로브 경로를 `/** … */` 안에 적으면 `skills/*` 다음의 `/`에서 **주석이 먼저 닫히고** 남은 글자가 코드로 파싱된다(TS1443 + TS1160). 같은 계열로 템플릿 리터럴 안의 백틱도 문자열을 끊는다(`lib/family/svg.ts`, 2026-08-15). 둘 다 실제로 빌드를 세웠고 원인이 주석이라 눈에 안 띈다. 경로를 적어야 하면 `<이름>`으로 쓴다.

astryx는 **사전컴파일 CSS와 컴파일이 끝난 JS를 배포**한다. 그래서 StyleX 빌드 도구(babel-plugin·PostCSS)를 붙이지 않는다. `@stylexjs/stylex` peer는 컴파일러가 아니라 **런타임 클래스명 조립기**다. 다만 **우리 코드가 `stylex.create`를 직접 호출하면** Vitest 트랜스폼에 StyleX 컴파일이 실제로 돌아야 한다 — 그 선을 넘기 전에 헌장을 고친다.

**버전을 캐럿으로 열어두지 않는다.** astryx는 최초 발행 7주 만에 0.1.0 → 0.4.0이고 마이너마다 prop 이름이 바뀐다. 올릴 때는 의식적으로 `astryx upgrade --apply`를 돌린다.

### 라이브러리를 추가하는 규칙

1. **표준 라이브러리·플랫폼 기능으로 되는지 먼저 본다.** CSS로 되는 걸 JS 라이브러리로 하지 않는다
2. **이미 있는 의존성으로 되는지 본다**
3. 그래도 필요하면 **버전·라이선스·최종 배포일을 확인하고 이 표에 적는다.** 기억으로 쓰지 않는다
4. MPL-2.0 이상 강한 카피레프트는 표에 굵게 표시한다

### 문서 프레임워크는 쓰지 않는다

Starlight·Nextra·Fumadocs를 검토하고 접었다. astryx와 CSS가 부딪히는 것이 조사에서 지목된 최대 위험이었고, 내비게이션은 어차피 손으로 고른다. 크롬은 astryx 컴포넌트로 직접 조립한다.

```
├── entities/<타입>/<이름>.md     객체 노트 644개
├── points/*.md                  편역본 본문 34개
├── source/*.md                  기번 영문 원전 72개
│
└── site/                        ← 사이트 코드. 여기부터가 이 헌장의 범위
    ├── CONSTITUTION.md          이 파일
    ├── AGENTS.md                사이트 코드 규칙 + 상위 규칙으로 가는 다리

    │   ├── config.yaml          이 헌장의 기계 판독 부분
    │   ├── changes/             진행 중인 변경 제안
    │   └── specs/               확정된 동작 명세
    │
    ├── lib/                     ★ 공용 + 서비스 로직. 로직은 전부 여기 산다
    │   ├── ontology.ts          데이터 계약 (스키마 · 로더 · 불변식) — 정본
    │   ├── ontology.test.ts     계약 테스트
    │   └── <도메인>/             도메인별 서비스. 아래 규칙 참조
    │
    ├── components/              ★ UI 컴포넌트. 상태와 표현만
    ├── app/                     ★ 라우팅. 조립만 하고 로직을 두지 않는다
    ├── e2e/                     ★ Playwright 시나리오
    ├── public/                  정적 자산. atlas/가 여기 통째로 들어온다
    └── out/                     빌드 산출물. 커밋하지 않는다
```

### 경계 규칙 (리뷰에서 본다)

| 층 | 두는 것 | 두지 않는 것 |
|---|---|---|
| `lib/ontology.ts` | 스키마·로더·불변식. **다른 어디에도 스키마를 두지 않는다** | 화면에 대한 지식 |
| `lib/<도메인>/` | 데이터를 읽고 화면이 쓸 모양으로 바꾸는 순수 함수 | React import, DOM 접근 |
| `components/` | 받은 값을 그리는 일 | 파일 읽기, jsonl 파싱, 비즈니스 규칙 |
| `app/` | 라우트 정의, `generateStaticParams`, 조립 | **로직 일체.** 세 줄 넘는 변환이 보이면 `lib/`로 내린다 |
| `e2e/` | 사용자가 실제로 하는 일 | 구현 세부 |

**`lib/<도메인>/`은 React를 import 하지 않는다.** 이 한 줄이 지켜지면 서비스 로직은 항상 테스트하기 쉽고, 깨지면 어디가 깨졌는지 바로 보인다.

도메인은 데이터의 결을 따른다: `entity`(객체 조회) · `relation`(관계 질의) · `timeline`(연도 구간) · `text`(본문·위키링크) · `export`(시트 내려받기). 필요할 때 만들고 미리 만들지 않는다.

### 테스트가 사는 곳

- **유닛·계약**: 대상 파일 옆에 `*.test.ts` — `lib/ontology.ts` 옆에 `lib/ontology.test.ts`. 멀리 두면 같이 안 고친다
- **컴포넌트**: 컴포넌트 옆에 `*.test.tsx`
- **E2E**: `e2e/*.spec.ts`. 유일하게 대상과 떨어져 사는 테스트다 — 화면 하나에 대응하지 않기 때문이다
- 노드 API가 필요한 테스트는 파일 첫 줄에 `// @vitest-environment node`

## 5. 데이터 계약이 이 프로젝트의 급소다

깨지는 자리는 버튼이 아니라 데이터다. 데이터는 계속 갱신되고, 갱신할 때마다 링크가 끊어지거나 타입이 어긋날 수 있다.

1. **스키마 정본은 `lib/ontology.ts` 하나다.** 빌드 게이트와 테스트가 같은 것을 import 한다. 두 벌로 쓰면 로컬에서 통과한 게 배포에서 깨진다
2. **`npm run build`가 `npm run validate`를 먼저 돌린다.** 불변식이 깨지면 빌드가 멈추고 팀은 틀린 데이터를 볼 일이 없다
3. **알려진 위반은 `KNOWN_VIOLATIONS`에 이유와 함께 적어 통과시킨다.** 목표는 "위반 0"이 아니라 **새 위반이 늘지 않는 것**이다. 0으로 만들려고 억지로 배정하면 데이터가 오염된다
4. **고친 위반은 목록에서 지운다.** 안 지우면 그 자리의 다음 회귀를 못 잡는다. 별도 테스트가 이걸 강제한다
5. `KNOWN_VIOLATIONS`에 **이유 없이 줄을 추가하지 않는다.** 그 순간 이 테스트는 아무것도 막지 않는다

사이트는 데이터를 **읽기만 한다.** 수정이 필요하면 `../.agent/skills/propose-change/` 절차를 따른다.

## 6. 개발 방식 — TDD Red-Green-Refactor

### 순서

```
0. 스펙      /opsx:propose "무엇을 왜"        →  openspec/changes/
1. RED       실패하는 테스트를 먼저 쓴다        →  npm test 가 빨갛다
2. GREEN     통과할 만큼만 쓴다                →  npm test 가 초록이다
3. REFACTOR  초록을 유지한 채 정리한다          →  npm test 가 여전히 초록이다
4. 리뷰      아래 7절                        →  공통 로직·중복 검사
5. 마무리    /opsx:archive                   →  openspec/specs/ 로 확정
```

### RED 단계에서 지킬 것

- **테스트를 먼저 쓴다.** 구현하고 나서 테스트를 붙이면 그 테스트는 구현을 따라 쓴 것이라 아무것도 못 잡는다
- **테스트가 실패하는 것을 눈으로 본다.** 통과하는 걸 보고 넘어가면 그 테스트는 애초에 아무것도 검사하지 않았을 수 있다
- 실패 메시지가 **무엇이 왜 틀렸는지** 말하는지 확인한다. `expected true to be false`는 실패한 테스트가 아니라 실패한 설계다
- 테스트 이름은 **동작**을 한국어로 적는다. `it('연도가 없는 링크는 구간 질의에서 빠진다')`

### GREEN 단계에서 지킬 것

- **통과할 만큼만 쓴다.** 나중에 필요할 것 같은 코드를 미리 쓰지 않는다
- 추상화를 여기서 만들지 않는다. 추상화는 3단계에서, 중복이 실제로 보인 뒤에

### REFACTOR 단계에서 지킬 것

- 테스트를 고치지 않는다. **테스트를 고쳐야 통과한다면 그건 리팩토링이 아니라 동작 변경**이고, 1단계로 돌아가야 한다
- 매 변경마다 테스트를 돌린다

### 테스트를 안 써도 되는 것

YAGNI는 테스트에도 적용된다. 다음은 테스트 없이 간다.

- 한 줄짜리 통과 함수, 상수 정의
- `app/` 아래 순수 조립 코드 (E2E가 덮는다)
- 외부 라이브러리가 이미 보장하는 것

**반대로 반드시 테스트가 있어야 하는 것**: 데이터 로딩·변환, 위키링크 URL 치환, 시트 내보내기, 연도 계산, 불변식 검사. 여기가 이 프로젝트의 위험이 사는 곳이다.

## 7. 개발 완료 후 코드 리뷰 — 닫기 전에 반드시 한다

**초록이 됐다고 끝이 아니다.** 변경을 아카이브하기 전에 리뷰를 한 번 더 돈다. 목적은 버그 찾기가 아니라 **공통 로직 발견과 중복 제거**다.

### 리뷰 체크리스트

**① 중복·공통 로직**
- [ ] **astryx에 이미 있는 컴포넌트를 손으로 다시 만들었는가** — `dist/`를 먼저 본다 (3절)
- [ ] 이번에 쓴 코드와 **같은 일을 하는 것이 `lib/`에 이미 있는가** — 먼저 찾고 나서 쓴다
- [ ] 같은 변환이 두 군데 이상 있는가. **세 번째가 나타나면 반드시 `lib/`로 올린다** (두 번은 아직 우연일 수 있다)
- [ ] 같은 상수·문자열이 흩어져 있는가
- [ ] 비슷한 테스트가 반복되는가 — 픽스처로 묶을 자리인가

**② 경계**
- [ ] `app/`에 로직이 들어갔는가 (세 줄 넘는 변환이 보이면 내린다)
- [ ] `lib/<도메인>/`이 React를 import 하는가
- [ ] `components/`가 파일을 읽거나 jsonl을 파싱하는가
- [ ] 스키마가 `lib/ontology.ts` 밖에 또 있는가

**③ 데이터 계약**
- [ ] `KNOWN_VIOLATIONS`가 늘었는가. 늘었다면 **이유가 적혀 있는가**
- [ ] 고친 위반을 목록에서 지웠는가
- [ ] 빌드 게이트를 우회한 자리가 있는가

**④ 죽은 것**
- [ ] 쓰지 않는 export·import·파일·의존성
- [ ] 주석 처리된 코드 (지운다. 이력은 git에 있다)
- [ ] "나중에 쓸 것 같아서" 남긴 추상화

**⑤ 0절 — 이걸 왜 만들었나**
- [ ] 이 변경이 **헷갈림을 덜어주는가, 우리가 만든 걸 보여주는가** (0절 판정 질문)
- [ ] `USECASE.md` 여섯 단계 중 어디에 걸리는가. 아무 데도 안 걸리면 왜 지금 만들었는지 적는다

**⑥ 테스트 자체**
- [ ] 테스트가 구현 세부가 아니라 **동작**을 검사하는가
- [ ] 이 테스트는 무엇이 깨지면 빨개지는가. 답이 없으면 지운다
- [ ] 느려진 테스트가 있는가

### 리뷰 결과 처리

- 고칠 것이 나오면 **고치고 테스트를 다시 돌린 뒤** 아카이브한다
- 지금 안 고치기로 한 것은 **부채로 명시한다** — `openspec/changes/<변경>/`에 남기고, 왜 미루는지 적는다. 조용히 넘기지 않는다
- 리뷰 없이 아카이브하지 않는다

## 8. 어긋나면 안 되는 것 (요약)

리뷰에서 이것들이 깨졌으면 되돌린다.

0. **0절의 판정 질문을 통과하지 못하는 기능은 넣지 않는다.** 코드 품질과 무관하게 되돌린다
1. **백엔드를 만들지 않는다.** 서버가 필요하면 헌장을 먼저 고친다
2. **스키마는 `lib/ontology.ts` 하나다**
3. **`app/`에 로직을 두지 않는다**
4. **`lib/<도메인>/`은 React를 모른다**
5. **테스트를 나중에 붙이지 않는다**
6. **`KNOWN_VIOLATIONS`에 이유 없이 줄을 넣지 않는다**
7. **사이트 코드로 `../ontology/*.jsonl`을 쓰지 않는다** — 읽기만 한다
8. **볼트에 `node_modules`가 들어가지 않는다** — 코드는 레포, 문서는 볼트
9. **라이브러리 버전·라이선스를 기억으로 적지 않는다** — 확인하고 3절 표에 적는다
10. **리뷰 없이 닫지 않는다**

## 10. 이 헌장의 위치

- 기계가 읽는 부분은 `openspec/config.yaml`의 `context`·`rules`·`operations`에 있다. OpenSpec이 스펙을 만들 때 그걸 읽는다
- 사람이 읽는 전문은 이 파일이다. **단 정본은 볼트 쪽이다**
- **왜 이렇게 정했나**는 볼트 `Works/로마쇠망사_자료실/`에 있다

| 볼트 문서 | 무엇 |
|---|---|
| `CONSTITUTION.md` | 이 파일의 정본 |
| `USECASE.md` | 0-2가 말하는 진짜 쓰임 하나 |
| `SPEC.md` · `PLAN.md` | 무엇을 · 어떻게 |
| `TASKS.md` · `CLARIFY.md` | 작업 순서 · 미결 |
| `DESIGN.md` · `CONTENT.md` | 화면 · 문구 |
| `USAGE.md` | 활용 레시피 (사이트 「활용하기」의 정본) |
| `RESEARCH.md` · `RISK.md` · `ANALYZE.md` | 미지수 · 위험 · 일관성 점검 |
| `Context/` | 접힌 초안과 판단 근거 |

- 데이터를 다루는 규칙은 여기 없다. 레포 루트 `../AGENTS.md`가 정본이다
