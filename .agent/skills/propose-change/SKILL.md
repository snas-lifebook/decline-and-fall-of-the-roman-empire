# propose-change

## 언제 쓰는가

`entities.jsonl` 또는 `links.jsonl`에 새 객체·새 관계를 더하거나 기존 항목의 오류(오타, 잘못된 연도, 끊어진 링크)를 고치자는 요청을 받았을 때. 이 스킬은 **제안 파일을 만드는 것**으로 끝난다. 파일을 직접 쓰거나 고치는 작업이 아니다.

여러 AI가 같은 jsonl을 동시에 쓰면 경합이 난다. 2026-08-11에 한 에이전트가 `links.jsonl`을 재작성하는 사이 다른 에이전트가 읽어 항목 5개가 조용히 사라진 사고가 실제로 있었다. 그래서 쓰기 권한은 사람에게만 있고, AI는 `/tmp`에 제안만 남긴다.

## 입력

- 무엇을 추가/수정하고 싶은지에 대한 요청 또는 관찰
- 근거가 될 원문(본문 줄 번호, 사료명)
- 기존 `entities.jsonl`·`links.jsonl` 읽기 접근

**타입 7종**: person · place · event · group · institution · work · period

**rel 11종만 허용**: `child_of` `succeeded` `allied_with` `opposed` `participated_in` `occurred_at` `ruled` `member_of` `married` `conquered` `created`

**실제 스키마** — 지어내지 말고 이 모양을 그대로 따른다. 파일에서 한 줄 읽어 확인하는 것이 가장 확실하다.

`entities.jsonl` 한 줄:

```json
{"id": "person:가비니우스", "name": "가비니우스", "type": "person", "aliases": [], "attrs": {"role": "consul", "period": "공화정 말기"}, "points": [6], "desc": "카이사르의 부하로 카이사르의 지지로 집정관에 당선된 인물.", "descs": [{"point": 6, "desc": "카이사르의 부하로 ..."}], "note": "가비니우스"}
```

`links.jsonl` 한 줄:

```json
{"from": "person:로물루스", "to": "place:로마", "rel": "ruled", "point": 1, "from_year": -753, "to_year": null, "year_basis": "chronology"}
```

주의할 자리 넷.

- **`id`는 `<타입>:<이름>` 형식**이다. `per_gaius_duilius` 같은 임의 slug가 아니다
- **`points`는 포인트 번호 정수 배열**이다(`[6]`). 설명을 넣는 자리가 아니다
- **설명은 `desc`(대표 한 줄)와 `descs`(포인트별 `{point, desc}` 배열) 둘 다** 채운다
- **`point`는 정수**다. `year_basis`는 `chronology` · `text` · `inferred` 셋 중 하나이거나 `null`이다. 다른 값을 쓰지 않는다

## 절차

1. **무엇을 왜 바꾸는지 한 줄로 적는다.**
2. **근거를 먼저 확보한다.** 본문 몇 번째 줄인지, 어느 사료인지 명시한다. 근거 없이는 제안을 만들지 않는다.
3. **대상이 이미 있는지 확인한다.** `entities.jsonl`을 이름·별칭으로 검색한다(`grep -n "이름" entities.jsonl` 또는 `aliases` 필드까지 훑는 스크립트 사용). 동명이인일 수 있으므로 아래 「하지 말 것」의 동명이인 항목을 먼저 읽는다.
4. **불변식 여섯을 하나씩 대조한다.**
   1. 객체 하나에 노트 하나 — 새 객체를 제안하면 `entities/<type>/<이름>.md` 노트도 같이 제안한다. 이름·타입이 겹칠 때만 파일명에 `(지명)`·`(집단)` 같은 접미사를 붙이고, jsonl의 `name`은 접미사 없이 그대로 쓴다.
   2. rel은 11종 중 하나인가. 아니면 데이터를 만들지 말고 rel 신설을 먼저 논의한다.
   3. 연도 부호 — 기원전은 음수, 서기는 양수. `year_basis`도 함께 채운다.
   4. `occurred_at`의 주어(`from`)는 반드시 event인가.
   5. `participated_in`은 인물·집단 → 사건 방향인가.
   6. `from`·`to`가 모두 `entities.jsonl`에 실재하는 id인가.
5. **`/tmp`에 제안 파일을 쓴다.** 레포의 `entities.jsonl`·`links.jsonl`·`entities/*.md`는 손대지 않는다.
6. 사람이 검수하고 병합한다. 병합 전까지 이 제안은 초안일 뿐이다.

## 하지 말 것

- **`entities.jsonl`·`links.jsonl`을 직접 고치지 마라.** 5개 항목이 조용히 사라진 사고가 그렇게 났다.
- **없는 관계를 억지로 만들지 마라.** 배경 언급뿐인 지명에 링크를 다는 것보다 비워 두는 편이 낫다. 예: 곶(지명)이 그리스와 `allied_with`일 수 없다. 투리이는 로마에 보호를 요청했을 뿐 동맹을 맺지 않았다 — 이런 관계는 제안하지 않는다.
- **표현할 rel이 없다고 비슷한 걸 갖다 쓰지 마라.** 그렇게 `occurred_at` 오용 37건, 인물→지명 `participated_in` 오용 20건이 쌓였다. 자리가 없으면 "이 관계는 표현할 rel이 없다"고 보고하고 rel 신설 논의로 넘긴다. 데이터에 억지로 끼워 넣지 않는다.
- **동명이인을 설명 유사도로 판정하지 마라.** 카이사르처럼 한 인물의 포인트별 서술은 국면이 달라 유사도가 낮게 나올 수 있다. alias 신호도 못 믿는다 — 실제 검증한 12쌍 중 4쌍이 서로 다른 인물이었다. 포인트별 서술을 사람 눈으로 대조해 판정한다. 확신이 안 서면 판정하지 말고 사람에게 넘긴다.
- **연도·인과를 추정으로 채우지 마라.** AI가 가장 자주 틀리는 자리다. 과거 제안 68건 중 19건이 반려됐는데 연도 혼동이 큰 몫이었다 — 마르살라 만 해전을 -241로 적었으나 본문 순서상 -256이 맞았고, 탈라모네를 -240으로 적었으나 실제는 -225였다. 모르면 `confidence: low`로 표시하거나 아예 제안하지 않는다.
- **`entities/*.md`를 손으로 대량 수정하지 마라.** 이 파일들은 `ontology/_scripts/rome30_*.py`가 재생성한다. 그 파이프라인은 `merge → geo → maps → backlink` 순서를 지켜야 하며, `merge`만 단독 실행하면 하류가 붙인 좌표·지도 섹션이 지워진다. 노트 변경도 제안으로만 남긴다.

## 출력 형태

제안 파일은 `/tmp/rome-proposals/<주제>.md` 로 쓴다. 아래는 신규 객체 하나와 신규 관계 하나를 담은 예시다.

```markdown
## 제안: 가이우스 두일리우스 신규 등록 + 밀라이 해전 참전

### 무엇을
- 신규 person 객체 `person:두일리우스`
- 신규 관계 `person:두일리우스 --participated_in--> event:밀라이해전`

### 왜
포인트 02 본문이 로마 최초의 해전 승리 지휘관으로 서술하는데 entities.jsonl에 없다.

### 근거
- `points/02_제1차_포에니_전쟁.md` 본문 (해당 줄 번호를 적는다)
- 인용을 그대로 옮긴다

### 대상 확인
- `grep '"name": "두일리우스"' ontology/entities.jsonl` → 결과 없음. 별칭도 없음
- 대상 사건 `event:밀라이해전`이 실재하는지 확인 → **없다.** 포인트 02의 event는
  메시나전투 · 제1차포에니전쟁 · 아그리젠토포위 · 마르살라만해전 · 본곶전투 ·
  탈라모네전투 · 팔레르모탈환시도 일곱뿐이다
- 따라서 이 제안은 **사건 신설을 함께 제안하거나, 관계를 빼고 객체만 제안해야 한다**

### 불변식 대조
1. 노트 매핑 — `entities/person/두일리우스.md` 신규 제안 포함 (통과)
2. rel 유효성 — `participated_in`, 11종 내 (통과)
3. 연도 부호 — 음수 (통과)
4. `occurred_at` 주어 — 해당 없음
5. `participated_in` 방향 — person → event (통과)
6. 링크 무결성 — **`to`가 실재하지 않음 (실패)**. 사건을 먼저 만들어야 한다

### confidence
low — 대상 사건이 없어 관계 부분은 이대로 병합할 수 없다

### 신규 entities.jsonl 항목
{"id": "person:두일리우스", "name": "두일리우스", "type": "person", "aliases": ["가이우스 두일리우스"], "attrs": {"role": "consul"}, "points": [2], "desc": "제1차 포에니 전쟁에서 로마 최초의 해전 승리를 이끈 집정관.", "descs": [{"point": 2, "desc": "제1차 포에니 전쟁에서 로마 최초의 해전 승리를 이끈 집정관."}], "note": "두일리우스"}
```

**이 예시는 일부러 실패하는 항목을 담고 있다.** 불변식 6번이 걸려서 관계는 병합할 수 없다. 제안이 통과하지 못하는 것을 발견하는 것도 이 스킬의 성과다. 억지로 통과시키려고 없는 사건을 지어내는 순간 데이터가 오염된다.

기존 항목을 고치는 정정 제안도 형태가 같다. 「무엇을」에 현재 값과 정정 값을 나란히 적는다.

```markdown
## 제안: 포인트 02 연도 부호 정정

### 무엇을
`links.jsonl`의 `point: 2` 항목 중 `from_year`·`to_year`가 양수인 것들.
현재 `"from_year": 264` → 정정 `"from_year": -264`

### 왜
포인트 02는 전 구간이 기원전 사건인데 부호가 빠져 제1차 포에니 전쟁이
서기 3세기에 찍힌다.

### 근거
같은 포인트의 다른 항목이 음수이고, `chronology.csv`가 기원전 264~241년을 준다.

### 불변식 대조
3번(연도 부호)이 핵심. 나머지는 변경 없음.

### confidence
high
```

한 파일에 여러 항목을 묶어도 되지만, 항목마다 무엇을·왜·근거·대상 확인·불변식 대조·confidence 여섯을 각각 갖춘다.
